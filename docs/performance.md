# 性能基线与测量口径

这份文档只回答两件事：**怎么量**、**量出来是多少**。改性能相关代码前先量一遍，改完再量一遍，
拿数字说话——这一层最容易凭感觉改错地方。

## 1. 两种启动口径，回答两个不同的问题

| 启动参数 | 回答什么 | 注意 |
| :--- | :--- | :--- |
| `--remote-debugging-port=9222` | **这台机器这把刷新率上有没有掉帧**：看超预算帧的比例与长任务 | 帧率受 vsync 限制，跨机器比较没意义 |
| 加上 `--disable-gpu-vsync --disable-frame-rate-limit` | **每帧真实成本**：rAF 不再等垂直同步，每帧毫秒数就是主线程工作量，可换算出任意刷新率的余量 | 这种口径下"每秒帧数"没有意义，别拿去做横向比较 |

两种都必须是**生产构建**（`npm run build:server` + `apps/desktop` 的 `build` + `electron-builder --dir`），
dev server 带 HMR，帧数据不可比。

**窗口必须在前台可见**：后台或被整块遮挡时 Chromium 会停掉帧的生产，rAF 直接停摆，量出来全是假的。
脚本开头会打印 rAF 节拍，`p50` 明显偏离刷新间隔就先解决可见性。

## 2. 怎么跑

两个脚本都在 `tools/transcript-perf/`，零依赖（Node ≥ 22，用内建 `fetch` 与 `WebSocket` 走 CDP）：

```bash
# 帧预算：边流式边滚，出每帧 p50/p95/max、超预算帧、长任务、每秒各项占用
node tools/transcript-perf/stream-frames.mjs --port 9222 --session 性能测试 --rows 300

# 测高与落点：全量扫描耗时、文档高度锁定、双向长途跳转、连点、改宽重测
node tools/transcript-perf/measure.mjs --port 9222 --session 性能测试 --rowsA 182 --rowsB 320
```

两个脚本都会先把行数补到指定值再开测（用竖轨顶端的「…」逐页补）。**这一步不能省**：主机每五分钟
会静默回收更早的历史（`54ab035`），大会话自己会缩水，不补的话量到的是小会话。

要函数级归因时用 CDP 的 tracing（`devtools.timeline` + `disabled-by-default-devtools.timeline`），
按 `FunctionCall` 的 `functionName` 聚合；需要看源码位置的再临时开 `build: { sourcemap: true }`，
**测完必须改回去**。

## 3. 基线（2026-11-26，Linux，100Hz 屏，不限帧口径）

会话：「性能测试」336 行 / 49,797 正文元素 / scrollHeight 约 14 万 px。

### 每帧主线程工作量

| 阶段 | p50 | p95 | max | 长任务 | Script | Recalc |
| :--- | ---: | ---: | ---: | :--- | ---: | ---: |
| 流式 + 不滚 | 1.0ms | 1.4ms | 16ms | 0 | 139ms/s | 69ms/s |
| **流式 + 往上滚** | **2.0ms** | **7.7ms** | 17.6ms | 0 | 109ms/s | 54ms/s |
| 流式 + 往下滚 | 2.0ms | 7.5ms | 17.5ms | 0 | 110ms/s | 43ms/s |
| 不流式 + 往上滚 | 1.5ms | 6.7ms | 17ms | 0 | 59ms/s | 20ms/s |

### 换算：p95 决定"持续不失帧"的能力

| 刷新率 | 每帧预算 | p50 用掉 | p95 用掉 | 结论 |
| :--- | ---: | ---: | ---: | :--- |
| 60Hz | 16.7ms | 12% | 46% | 余量充足 |
| 100Hz | 10.0ms | 20% | 77% | 满帧，余量约 23% |
| 120Hz | 8.3ms | 24% | 92% | 基本满帧，余量 8% |
| 144Hz | 6.9ms | 29% | 111% | 会掉帧 |
| 160Hz | 6.3ms | 32% | 123% | 掉帧可见 |
| 180Hz | 5.6ms | 36% | 139% | 掉帧明显 |
| 240Hz | 4.2ms | 48% | 185% | 明显掉帧 |

即"边流式边滚"的实际上限约 **130fps**（1000 / p95）。

### 关键比例：JS 只剩小头

同一工况下 `Task` 约 730–755ms/s，而 `Script` 只有约 109ms/s —— **主线程忙的时间里约 85% 不是 JS**，
是 Layerize / Paint / 合成提交。也就是说想来再往上，改 JS 没有多少空间，得减 DOM。

## 4. 已知瓶颈与下一步

| 目标 | 需要做什么 |
| :--- | :--- |
| 稳住 100Hz / 120Hz | 已经够了 |
| 撑到 144Hz 以上 | 只能靠**分段挂载**（几万元素降到一万级，Layerize/Paint 按比例降）|
| 内存 | 同样靠分段挂载；当前 heap 在 100MB 级、随行数线性增长 |

## 5. 历史（2026-11-26 那一轮修复前后）

同一会话规模、同一动作（流式 + 200 个滚轮事件），前面的数字是修复前：

| | 修复前 | 修复后 |
| :--- | ---: | ---: |
| 实测 FPS | 75.5 | 99.4 |
| p95 | 29.9ms | 10.1ms |
| 超 16.7ms 的帧 | 145/593（24%）| 2/333（1%）|
| 长任务 | 4 × 72ms | 0 |

那一轮动到的六处：`.app:has()` 换成属性（样式失效按整棵树重验）、流式时已结束的工具段沿用对象、
竖轨锚点按键指纹失效、滚动路径去掉 O(行数) 的锚点扫描、流式期间不跑全量重测、竖轨当前轮次从上一帧
结果就近探查、流式解析打开顶层块节点沿用。
